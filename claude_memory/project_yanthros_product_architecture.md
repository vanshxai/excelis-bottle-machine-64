Three pieces, decided Sep 2026: (1) **Core engine** — `~/Desktop/faulter-formula-brain` (333 formulas, `brain.py`+`formulas.py`), never shipped whole. (2) **Software packet builder** — per-machine, built from a scoped formula subset, takes the client's STEP/BOM upload and produces (3) an **exe** with the 3D twin + fault-signature DB. Code: `~/Desktop/excelis/license_prototype/` (`step_parser.py`, `formula_selector.py`, `packet_builder_app.py`, `twin_viewer_build/`, `fault_sweep_generator.py`). Local admin dashboard (dark, offline, port 5090): `license_prototype/dashboard/` — Graph Explorer + Solver panels; releases are published there for the user to download.

Business/licensing decisions: one packet per machine; **perpetual license, no PC/hardware fingerprint lock** ("Unreal Engine model") — enforcement is the signed contract, royalty when the client reuses it for further clients. Signature check + encrypted payload kept; no invented crypto, no self-destruct. Client intake is a 10-question form when no CAD exists, STEP (not eDrawings) when it does.

**Why:** eDrawings/SolidWorks binaries are unparseable here; STEP is an open standard. Proven on a real NIST file and an Adafruit servo file.

**How to apply:** don't push into the existing GitHub repos `vanshxai/faulter_core_new` or `vanshxai/yanthros` (different prior code); core+Zinaata lives in `vanshxai/yanthros-zinaata`. `git` binary is broken (no Xcode CLT) — use `gh api` contents endpoint to push. `brain_graph.json` copies in `YANTHROS CORE/` and the GitHub repo are stale (946 nodes/420 edges vs live 804/333); the one in `faulter-formula-brain/` was refreshed on 2026-09-21 by an early dashboard bug. `brain.build_graph()` WRITES that file — never call it from a page handler; the dashboard computes stats in memory.

Zinaata (phone diagnosis, same method retargeted): `~/Desktop/Zinaata` (macOS Swift app) and `~/Desktop/ZinaataAndroid` (backend, webapp, component_database). **DORUSSS** = the 7-stage ML/RL diagnosis pipeline there (`backend/dorus_engine.py`, `rl_diagnosis/DORUSSS_REPORT.md`); its own report shows the RL agent at 32.5% vs 92.6% for the full-sensor model. **Update 2026-10-03 (user decisions, supersede the builder->exe chain above):** collapse builder + generated exe into ONE offline installable app per machine. It ships with the scoped formula "lego stock" + wireframe maker; the client feeds in their BOM + assembly (STEP) files inside the app and it builds the wireframe + per-machine backend itself. Client refuses to share assembly files (proprietary), so there is NO pre-check by us; we rehearse on open-source assemblies instead. Hard rule: ZERO GUESSES. If any value is missing the app must stop and ask, and may abandon setup rather than assume anything (current code that guesses: the engine's ESP32 default knowns and the fault-sweep's assumed resistances; both must be off in the app). Licensing: Windows-style license + contract, royalty per machine paid from the client's own sales records/official statements; copying is free technically, NO activation-key counting, NO cloud / phone-home (client forbids cloud). Reinstalling for another same-design machine, or duplicating the built project, is fine.

**STEP reader decision (2026-10-04, step 1 of the Bottle Machine 64 build):** use `cascadio` (+ trimesh/numpy) in `bottle_machine_64/.venv`; `engine/step_geometry.py` returns per-part world-space edges, bbox and assembly nesting. Do NOT use `cadquery-ocp`: every available version links VTK (223MB + 115MB vtk). cascadio is ~71MB. Reading time is dominated by STEP parsing, not meshing: Voron 0.2 (179MB STEP, 1991 parts) takes ~4-7 min once, so import needs a progress bar and caching. Real exports can have unnamed bodies (Fusion exports give names like `=>[0:1:1:1172]_a26870`), so classification must ask the user. `cascadio.step_to_glb(include_brep=True)` can expose cylinder/plane radii and axes later (useful for pulley/shaft sizes). Test files: `bottle_machine_64/spike/` (viewer + Voron 0.2 STEP in `spike/ext/`).

Gear-motor prototype reference (fetched 2026-10-06): original at `~/Desktop/150rpm gear motor prototype/Vansh/150rpm gear system/` (Flask app port 5053, package `gearsystem/`, ESP32+INA228 over USB serial); read-only copy in `bottle_machine_64/reference/gear_prototype/`. What actually detected faults live was "Part Interruption": 256-sample block mean (~0.29 s), idle <25 mA, fixed MEASURED absolute-current band per gear (Red 31-34, Green 35-42, Blue 43-90, Yellow >91 mA over a ~22 mA idle), 0.25 s hold, sticky lock until current returns to idle. The physics twin was never validated (motor Kt/Ke unmeasured; it predicted 1.6-4.5 mA for a light touch vs real bumps of roughly +9 to +70 mA) and its classifier is switched off (CLASSIFY_ENABLED=False). So simulated magnitudes vs real magnitudes is an open risk for the zero-recording approach. Parts nearer the motor gave bigger bumps (gear-ratio reflection). iPad/BLE apps (GearTwinLive, GearTwinDashboard) are untouched/paused.
**Physics validation done 2026-10-06** (`bottle_machine_64/validation/`: `validate_gear_prototype.py`, `REPORT.md`, `bands_vs_models.png`): the prototype's steady-state model was structurally wrong (efficiency counted from the output side, no gear-ratio reflection, lumped gain ~10x off; its RK4 model gave +-6..11 A). Corrected model: touch torque divided by speed reduction and mesh efficiency back to the motor shaft, current = torque/Kt with Kt=Ke=(V-I_idle*Ra)/omega_motor (derived from 12 V + 150 RPM output through the tooth chain, ~0.011-0.012 N*m/A). Spread-factor test (force differences needed between gears to hit the measured bands): prototype 18.9 -> fix efficiency direction 10.6 -> add ratio reflection 1.34 -> allow small wheels 0.75 (one common force fits). 1989 of 15912 registry-range combos fit. Engine `engine/gear_engine.py` (uses formula stock; new local formula `gear_reflected_torque`) matches an independent calc to 1e-16. Limits: only classification bands + idle current exist as real data (the July recordings DBs are the contaminated ACS712 era; no INA228 raw recordings on disk), touch force never measured. To prove absolute scale: record INA228 while pressing each gear with a known force (kitchen scale). Not yet wired into the Bottle Machine builder (needs a gear/belt-ratio coupling type).
**Formula flow dashboard + rulebook built 2026-10-06:** `/flow?name=<project>` (`app/static/flow.html`, API `/api/trace` via `engine/flow_trace.py`; `runtime.apply` records every formula step when tracing, solved expressions are cached so a full recompute is ~5-20 ms) shows every formula step for a chosen part and recomputes the whole chain when any value (load, part constants, motor nameplate, the three levels) changes; changed cells flash. Build now also writes `rulebook.json` (`engine/rulebook.py`): per motor, per part, the fine/elevated/warning/critical load ranges and the matching extra-current ranges, plus a "current ladder" saying which area to look at where parts overlap. The four level names/colours are the only style; their boundaries are the user's own three answers per part, no invented actions. Honest scope: each part's chain is a fixed series sequence, parallel only across parts; branch joins (loads summing at a shared driver), simultaneous faults and loops are NOT built (planned: a plan file + join step).
